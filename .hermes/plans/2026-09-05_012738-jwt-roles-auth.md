# Control Plane JWT + Roles + Claims Conversion — Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Convert the Project-D control plane from cookie-session (login) authentication to pure bearer-JWT authentication with maker/checker role claims and role-based enforcement, keeping the current Angular SPA working until it is retired in favor of the other app's UI. The `/api/login` endpoint becomes a config flag (`auth.jwt.login_enabled`) so the plane can later run external-JWT-only.

**Architecture:** JWT becomes the ONLY control-plane credential. `models.Session` gains a `Role` field; the JWT middleware materializes a `*models.Session{Username: sub, Role: roleClaim}` into the existing `sessionKey{}` request context, so every downstream consumer (`sessionFrom(r)`, SoD `checkerMayWatch`, audit, mint username-binding) keeps working unchanged. `/api/login` (flag-gated) issues self-signed HS256 JWTs; external-issuer trust (the other app's IdP) is a config slot ready for the follow-up phase but not wired to a real IdP here. Role enforcement: checkers may mint read-only tokens only + watch/kill sessions; makers may mint read-write and read-only tokens; makers watching/killing is gated by `auth.allow_maker_watch` (default false).

**Tech Stack:** Go (control plane), golang-jwt/jwt/v5 (new dep), Angular 21 + NG-ZORRO (SPA, to be retired later), Valkey (denylist + existing stores).

---

## Scope & Non-Goals

**In scope:**
- Cookie-session auth removed (`zt_session`, `sess:ui:*`, `requireSession`, `CreateSession/GetSession/DeleteSession`).
- `POST /api/login` + `/api/logout` registered ONLY when `auth.jwt.login_enabled: true`; login returns a JWT body (no cookie).
- `models.Session{Username, Role}`; JWT claims `sub` + `role` (`maker`|`checker`).
- Role enforcement: checker cannot mint write-access tokens (403); checker may watch/kill/list sessions; maker may watch/kill ONLY when `auth.allow_maker_watch: true`; SoD (watcher ≠ maker) preserved.
- Static `X-Api-Key` retired for control-plane API auth (`auth.api_key` / `ZT_API_API_KEY` removed). **The data-plane credential resolver's own `credentials_api.api_key` is a different key in a different process — UNTOUCHED.**
- SPA converted to JWT: login stores token, Authorization header on REST, `access_token` query param on the checker WS. SPA keeps working until retirement; no role-based route split in the SPA beyond what exists (maker portal / checker dashboard keep separate paths; role enforcement is server-side).

**Explicitly NOT in this phase:**
- Wiring the other application's real IdP — **trust direction is CONSUMER-ONLY: the other app generates JWTs, this control plane validates them** (JWKS public-key or shared-secret validation of an external issuer). This phase builds the validator as an issuer list (local issuer while `login_enabled` + reserved `external_issuers` slots) so the follow-up is config-only: add the other app's JWKS URL, flip `login_enabled: false`.
- "Mint for other users" via JWT-impersonation claims — the token body `username` still binds to the JWT `sub` (as today's session path binds to the session user). The other app's "mint tokens for its users" flow is a follow-up phase (needs a delegation rule: which issuer/principal may mint for a `username` ≠ `sub`).
- CORS for the other app's UI origin; OriginPatterns for cross-origin WS (reserved config, not wired to a real origin yet).
- Oracle/MySQL/MSSQL proxy internals — data plane is untouched by this phase.

## Config Design (target)

`configs/control.yaml` (auth block) + `.env.example`:

```yaml
auth:
  username: "admin"
  password: ""                # only required when auth.jwt.login_enabled (unchanged fail-fast)
  role: "maker"               # NEW: primary user's role
  # users: entries gain role (Task 9.13 list) — e.g. checker account role: "checker"
  users:
    - username: "checker"
      password: "${ZT_AUTH_CHECKER_PASSWORD}"
      role: "checker"         # NEW per-user role
  allow_maker_watch: false    # NEW: makers may watch/kill sessions when true
  jwt:
    enabled: true             # NEW master switch
    login_enabled: true       # NEW: register /api/login + /api/logout; self-issue HS256 JWTs
    issuer: "zerotrust-proxy" # NEW self-issuer name
    audience: "zt-api"        # NEW
    ttl_seconds: 28800        # NEW (8h; mirrors old session TTL; session_ttl_hours removed)
    secret: "${ZT_JWT_SECRET}"  # NEW; required when login_enabled; empty = refuse to start
    # external_issuers: []    # RESERVED for the other app's IdP (follow-up phase) — shape only
```

Validation rules (config.go):
- `auth.jwt.enabled == true` required going forward (or default true when absent).
- When `login_enabled`: `secret` non-empty fail-fast; `auth.username`/`auth.password` requirements unchanged.
- When `login_enabled == false`: username/password NOT required (plane may run external-only), secret not required.
- Role values: each `role` must be `maker`|`checker` (primary + users), fail-fast naming the offending entry.
- `session_ttl_hours` removed → replaced by `jwt.ttl_seconds`.
